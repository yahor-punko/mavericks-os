# Process State Rules

## PROCESS_STATE.json fields

```json
{
  "initiative": "...",
  "stage": "execution",
  "wave": 1,
  "wave_status": "planning",
  "wave_goal": null,
  "parked_waves": [],
  "active_slices": ["T-001", "T-002"],
  "next_action": "T-001 → developer → ...",
  "blocker": null,
  "stage_owner": "main_agent",
  "last_task_id": 2,
  "last_updated": "YYYY-MM-DD",
  "deploy_contours": 0,
  "wave_summary": "one-sentence summary written by --close-wave at wave end",
  "rechecks": []
}
```

`wave_status` — tracks architect review gate and wave lifecycle. Values: `planning` (default, wave being scoped) | `architect_reviewed` (architect review complete, tasks may proceed) | `execution` (tasks actively in progress). Waves with ≥3 planned tasks require architect review before the first task starts — Main Agent sets this to `architect_reviewed` after review. `--close-wave` resets `wave_status` to `planning` when it advances the wave — the ending wave's gate state must not carry forward onto the freshly opened wave (T-653). There is no `closed` value: the close and the wave-counter advance are one atomic write inside `--close-wave`, so a wave never sits in a persisted "closed" state — `wave_summary` is the record of what the closed wave accomplished.

`wave_goal` — optional string. One-line definition of done for the current wave. Set at wave open, with `--set-wave-goal "text"` (the sanctioned setter; an empty string clears), or via `--close-session` prompt when none is set; `--close-wave --next-goal` seeds the next wave's. Displayed in `--agent` digest and `--snapshot`. `--close-wave` clears it on advance and refuses to run while it is null unless the wave is parked. Default: null.

`wave_summary` — written automatically by `--close-wave` at the end of each wave; one sentence describing what the wave accomplished.

`rechecks` — optional array of time-based post-merge follow-up entries. Absent or empty means no rechecks and changes no existing behavior. Each entry is self-contained so it survives task archival: `id` (e.g. `"RC-1"`, sequential, assigned at arm time), `task` (e.g. `"T-123"`; optional when `wave` is present instead), `wave` (optional integer, e.g. `2`; a wave-keyed entry armed by `--park-wave --until` carries no `task` key), `title` (task title copied in at arm time, or an explicit title for a wave entry), `due` (absolute date `"YYYY-MM-DD"` when the recheck comes due), `interval` (optional, e.g. `"8w"`; supports weeks `w` and days `d`; used by `--ack-recheck --rearm` when no explicit `--due` is given), `armed_at` (`"YYYY-MM-DD"` when the recheck was created), `note` (optional free text). Managed via `--arm-recheck`, `--park-wave --until`, and `--ack-recheck`; to extend a park past its original date, use `--ack-recheck RC-N --rearm --due YYYY-MM-DD` rather than hand-editing `due`. See the **Recheck mechanism** convention below.

`parked_waves` — list of waves that remain open while a new wave proceeds; each entry is a string with the wave number and a one-line reason (e.g., `"Wave 2 — blocked on external review"`). Maintained via `--park-wave`/`--unpark-wave` (see the **Parked waves** convention below), which also relocate the wave's task blocks — not hand-edited directly.

`active_slices` — derived automatically by `--agent` from TASK_STATUS.md: only tasks with in-flight statuses (`in_progress`, `needs_fix`, `dev_done`, `ux_review`, `ux_passed`, `ux_needs_fix`, `security_review`, `security_passed`, `security_needs_fix`, `ready_for_qa`, `qa_in_progress`) are included — the single shared source of truth is `IN_FLIGHT_STATUSES` in `scripts/mavp-operator-lib.js`. The JSON field is informational only; `planned`, `qa_passed` (awaits the Main-Agent merge ritual, not sub-agent work), and `merged` tasks are excluded from the output.

`next_action` — a **routing directive only**, not a narrative log. Write it as either `T-NNN → role → short imperative action` (e.g. `"T-001 → developer → implement the parser"`) or, when no task is active, one short standalone imperative (e.g. `"Open next wave"`). It must NEVER embed a volatile fact that has no invalidation trigger once written — a claim that ASSERTS current state (`"the repo is at 0.42.1"`, `"currently on v1.2.3"`), unpushed-commit counts, ahead/behind push state, or external repo/mirror version state are all banned regardless of position. A version literal is judged by **position**, not by its mere presence (T-628/DR-009): one that names the **action-target** of the directive itself — the "`<verb> to X`" construction (`"bump to 0.44.3"`) or a literal immediately followed, with no intervening word, by a noun from a closed enumerated set (e.g. `"0.44.3 bump"`, `"the 0.44.3 section"`) — is exactly the fact the next developer/writer needs to complete the directive, so it is NOT flagged. That noun set's source of truth is the `ACTION_TARGET_FOLLOWER_NOUNS` constant in `scripts/mavp-operator-lib.js` (read by both `classifyNextAction()` and the validator's remediation text) — consult it directly rather than treating any list written here as normative. Adjacency is strict: a version literal separated from a follower noun by an intervening word still flags — `"the 0.44.3 stable promotion"` still flags, because `promotion` is not the immediate next token after the literal. A literal preceded by a state-assertion word (`is`/`are`/`at`/`on`/`now`/`currently`/`already`/`still`) is a state claim and IS flagged even when it could otherwise read as an action target — the state-assertion check wins ties. Those state facts already have a source of truth (`scripts/mavp-version.js`, `git`, GitHub) — reference the source, don't copy the value into `next_action`. Multi-fact cross-session narrative (what changed, why, what to check next session) belongs in `HANDOFF.md` (via `--handoff --notes "..."`) only, not in `next_action` — the wave strategy note (via `--set-strategy-note "..."`) is an intra-wave field that `--close-session` clears only on wave advance (T-648), surviving mid-wave closes verbatim, so it is still not a cross-session home once the wave actually closes; a wave-79-relevant note has already been erased at close before once and was only recovered because the operator still held it in context. Two shipped signals guard this shape: `classifyNextAction()` (in `scripts/mavp-operator-lib.js`) classifies the string using the position rule above, and `--agent` surfaces the result as additive fields `next_action_unverified` (true when `next_action` is non-empty and does not begin with `T-NNN`) and `next_action_volatile_facts` (an array of the matched volatile substrings, e.g. state-asserting version numbers or commit-count phrases). The validator emits the same check as a **failure-severity** finding named `next_action_volatile_facts` (DR-009: escalated from info to blocking — a rule the operator channel can silently violate must not stay advisory-only) — it blocks (exit 2) on a `next_action` write that fails the check.

`deploy_contours` — integer. Controls deploy pipeline visibility in `--agent` output. `0` = no deploy pipeline; `merged` is the final state; `deploy_queue` is always empty and deploy warnings are suppressed. `1` = single contour, auto-deploy-on-merge; `merged` = already deployed; `deploy_queue` is always empty and no `deploy_pending` state is set. `2` = dev + prod contours (default behavior when field is absent); `merged` tasks appear in `deploy_queue` as `deploy_pending: true`. Set to `0` for projects like mavericks itself where there is no separate deploy pipeline; set to `1` for projects where merge triggers an automatic deploy.

`last_task_id` — integer, the highest T-NNN assigned so far. Increment before registering a new task to avoid ID collisions. The validator checks for duplicate task IDs. The minting commands (`--new-task`, `--quick-task`, `--apply-decomposition`) write it at mint; the validator raises it only from `BACKLOG.md` Active Wave headings, as the info finding `last_task_id_auto_patched`; a block hand-registered in any other section leaves it behind until the next mint, which scans both artifacts whole and mints past that block.

**PROCESS_STATE.json is informational** — it is human-maintained and not validated for consistency with BACKLOG.md or TASK_STATUS.md. Do not use `next_action` or `active_slices` as authoritative truth; always verify against BACKLOG.md and TASK_STATUS.md directly.

## State-surface conventions

- **Recheck mechanism** — `rechecks` in `PROCESS_STATE.json` stores time-based, post-merge follow-up reminders: e.g. "retrain this model 8 weeks after merge" or "re-audit this config next quarter". An entry is either task-keyed (`task: T-NNN`, armed via `--arm-recheck`) or wave-keyed (`wave: N`, no `task` key, armed via `--park-wave --until` — see the **Parked waves** convention below). Use `--arm-recheck T-NNN --due YYYY-MM-DD [--interval 8w]` to register a task recheck; use `--ack-recheck RC-N` to dismiss it, or `--ack-recheck RC-N --rearm [--due YYYY-MM-DD]` to reschedule it (by its interval, or to an explicit date when `--due` is given — the only way to reschedule an interval-less wave-keyed entry). Every read-only surface judges due/overdue against the real clock, not `PROCESS_STATE.json`'s `last_updated` field, so a recheck due today always surfaces even if no state artifact was touched since it came due. Due rechecks surface in: the `--agent` JSON `due_rechecks[]` field (present only when entries are due, each flagged `overdue` when past due); a session-start callout; a `--snapshot` line; the operator dashboard "Due Rechecks" panel; and a non-blocking `overdue_recheck` advisory in the validator (info severity only — never blocks). Nothing fires between sessions — the framework has no daemon — so a team wanting a reminder outside a live session should run `./scripts/mavp-operator --snapshot` from an OS scheduler and grep its output for "Due rechecks:". Distinct from `stale_risk:` (see next note): `stale_risk` is a binary flag on an IN-FLIGHT task that guards staleness verification BEFORE merge; `rechecks` schedule a future revisit AFTER the task is already merged and archived. They are complementary — `stale_risk` covers the in-flight window; a recheck covers the post-merge interval.
- **Parked waves** — if a wave must remain open while a new wave starts, use `--park-wave [N] --reason "text" [--until YYYY-MM-DD]` (rather than hand-editing `parked_waves`): it relocates wave N's task blocks (and its trailing non-task sub-heading, so the same heading resurfaces on unpark) out of BACKLOG.md's Active Wave / TASK_STATUS.md's Active tasks into `## Wave N — Parked` / `## Parked tasks (Wave N)` sections (so the parked wave stops bloating session-start, size budgets, and next-action routing) and records `"Wave N — <reason>"` in `parked_waves`. A park may carry a resume date via `--until`, which arms a wave-keyed recheck (see the **Recheck mechanism** convention above) that surfaces as a due recheck on that date. Do not silently overlap waves. Use `--unpark-wave <N>` to restore the wave byte-for-byte when it resumes — this also auto-acks any `--until` recheck armed for that wave.
- **Must-read set** — `--agent` surfaces an additive `must_read` array at session start: files changed since the previous `--close-session` commit (found via git by matching the `chore: close session ...` marker) unioned with `context_docs` already resolved onto in-flight tasks. Computed by `computeMustRead()`/`getFilesChangedSincePreviousCloseSession()`/`findPreviousCloseSessionCommit()` in `scripts/mavp-operator-lib.js`; omitted entirely when empty, and degrades silently (no throw) when git is unavailable. The ledgers and live-state files (`MUST_READ_EXCLUDED_PATHS`: `BACKLOG.md`, `TASK_STATUS.md`, `PROCESS_STATE.json`, `PROCESS_STATE.md`, `EXECUTION_LOG.md`) are excluded by construction, as is every path starting with a `MUST_READ_EXCLUDED_PREFIXES` entry (`docs/archive/` — archived history is not reading; a plain root-relative prefix match, so `docs/archived-notes.md` and `sub/docs/archive/y.md` stay), and any remaining file whose decoded length exceeds `artifact_budgets.must_read_max_chars` (default 40000) moves to the additive `must_read_oversized: [{path, chars}]` field (emitted only when non-empty; split by `splitMustReadOversized()`). Rendered by the `session-start` skill as a "Must read" list plus a separate "Oversized (search, do not read whole)" list. In an adopter repo, installer-managed changed files appear in the additive `must_read_framework` field instead (emitted only when non-empty); declared `context_docs` stay in `must_read`.
- **Artifact brevity lint** — three info-severity, never-blocking validator advisories keep state artifacts lean: `artifact_size_budget` fires when `CLAUDE.md` or `HANDOFF.md` (whole-file, flat budget) or the `BACKLOG.md` Active Wave / `TASK_STATUS.md` Active tasks sections exceed their budget (archived wave sections are never counted); `state_in_claude_md` fires when `CLAUDE.md` contains task-state-shaped lines (`### T-NNN` headings or `- **Status:**` fields — task state belongs only in `BACKLOG.md`/`TASK_STATUS.md`); `context_size_budget` (T-782) measures the always-loaded context in characters — `CLAUDE.md` plus its recursive `@` imports (max four hops, resolved relative to the importing file, code spans and fenced blocks skipped) plus `.claude/rules` files that carry no `paths:` frontmatter — via `collectAlwaysLoadedContext()` in `scripts/mavp-operator-lib.js`, and fires once when the total exceeds `always_loaded_max_chars` (default 160000; the message names the top five contributors) and once per imported doc, unscoped rule, or module `context_docs` file over `imported_doc_max_chars` (default 40000); harness-owned content (auto-memory `MEMORY.md`, SessionStart hook output) is not counted. The unit of both `always_loaded_max_chars` and `imported_doc_max_chars` is JavaScript string length (`.length`, UTF-16 code units, not bytes), so a character outside the Basic Multilingual Plane such as an emoji counts as two; this is stated only for these two budgets, whose measuring code (`collectAlwaysLoadedContext()` and `checkContextSizeBudget()` in `scripts/mavp-validator.js`) was read for it, and the unit of any other `max_chars` budget is not asserted here. `claude_md_max_lines` is unchanged. The two Active-section budgets scale with the number of active tasks in that section: each resolves to `max(static_default, per_task_allowance × active_task_count)` (15 lines/task for BACKLOG Active Wave, 10 lines/task for TASK_STATUS Active tasks — see `mavp-validator.js` for the constants), so a legitimately large wave of many small tasks doesn't permanently trip the advisory. All budgets (including the two scaled ones, where an explicit override always wins over the computed value) are overridable per-field via an `artifact_budgets` object in `PROCESS_STATE.json` (e.g. `{"claude_md_max_lines": 400}`).
