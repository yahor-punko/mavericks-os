# Execution Log Rules

## Entry conventions

- **Lineage linkage — `EXECUTION_LOG.md` entry convention** — every `EXECUTION_LOG.md` entry must carry inline `T-NNN` and `DR-NNN` references for any task or decision it touches, so grepping a single `DR-NNN` id surfaces the decision record, every log entry that acted on it, and every task citing it. Pairs with the optional `Informed by:` / `Supersedes:` / `Tasks:` / `Session:` fields on decision records — see `docs/core/DECISIONS.md`. No graph-rendering tooling; this is plain grep over text artifacts.
- **Per-spawn outcome — `EXECUTION_LOG.md` entry convention** — every sub-agent spawn's entry also records `tool_uses: N/cap` and `outcome: completed|cap_hit|infra_failure|model_mismatch`, making the truncation rate greppable instead of eyeballed. The `cap` denominator IS the role's frontmatter `maxTurns` at spawn time (`.claude/agents/<role>.md`); any other denominator must name its source inline. Several recent entries carry a denominator matching neither the role's frontmatter value at spawn time nor a stated source — the artifacts alone cannot settle whether that reflects convention drift or a cap set outside this documented mechanism; treat it as an open question, not a resolved one. `outcome` follows `docs/core/ORCHESTRATION_RULES.md` — "Cap-hit triage": `completed` when the report ends in the completion token — this token-present case was already correct and is deliberately unchanged, even when `tool_uses` sits at or over cap; `cap_hit` when the token is absent and `tool_uses >= cap`; `infra_failure` when the token is absent and `tool_uses < cap`; `model_mismatch` when a Fable-only role's (architect, analyst, exa-researcher) report is discarded because its opening self-report line does not name the fable family (the discard-and-respawn rule), taking precedence over the other three values for that spawn. A convention over plain text, not a parser — harness-owned session JSONL carries no format contract to build one against. A Fable-only role's (architect, analyst, exa-researcher) spawn model label cites that report's own "Model self-report" opening line (see `docs/AGENT_SPEC.md` — "Model self-report"), never the Main Agent's spawn intent — forward-only, since `EXECUTION_LOG.md` entries are frozen and never retro-edited once written.
- **Registration home — `EXECUTION_LOG.md` entry convention** — a log entry is narrative, never a registration surface. Any reopen trigger, accepted boundary, or carried-forward finding recorded in an `EXECUTION_LOG.md` entry must also land, in the same session, in the artifact its consumer actually reads: a `Reopen trigger:` field in `BACKLOG.md`, a `docs/core/GATE_LEDGER.md` row, or a registered task. No validator check and no hook — same pull-consumed posture as the `Reopen trigger:` field itself (see the `Reopen trigger:` field convention above).
- **Gate-output quoting — `EXECUTION_LOG.md` entry convention** — a paraphrased push log cannot be audited: the `docs/core/GATE_LEDGER.md` T-763 row's reopen branches are ruled by grepping this log for the pre-push gate's literal lines, so a retold or missing line leaves the review unable to run its own method. Every entry recording a canonical push, a refused push attempt, or a stable promotion therefore quotes the whole literal output line verbatim in backticks — the checker's `Suite receipt: …` line, the hook's `PUSH REFUSED: …` line, the publish overlay's `Overlay complete: copied N, deleted N, preserved N` line — never a paraphrase. Forward-only and frozen, like the conventions above: entries are never retro-edited.
